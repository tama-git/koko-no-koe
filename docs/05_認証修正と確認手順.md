# 認証修正と確認手順

2026年10月30日。検証コミット `122de0db0830eec9ce6703864d49690c468c6d49` の不具合に対する修正です。

## 1. ログイン先とアカウントの違い

| 入口 | 認証するモデル | ログイン状態 |
| --- | --- | --- |
| `/login/` → `/dashboard/` | `AdminUser`。`is_active=True` かつ `is_staff=True` が必要 | DjangoのセッションCookie |
| `/admin/` | 既存のDjango標準 `auth.User` | Djangoの標準認証 |
| iPhoneから `/api/mobile/` | `MobileUser` | Bearerトークン。既存の `MobileSession` を使用 |
| `/mobile/login/`、`register/`、`index/`、`logout/` | 利用停止 | 案内画面を返し、登録・認証・ログアウトを実行しない |

「認証」は誰のアカウントかを確認すること、「権限確認」はその人が管理画面を使えるかを確認することです。`is_staff` は今回の独自管理画面の利用許可です。`is_superuser=True` だけで `is_staff=False` の場合も許可しません。

管理者専用の `AdminEmailBackend` がメールアドレスと保存済みのハッシュでパスワードを照合します。DjangoはセッションにユーザーIDと認証バックエンド名を保存し、次のアクセスでは同じバックエンドの `get_user()` が `AdminUser` を読み直します。別モデルの同じID・usernameでは代用しません。権限取り消し・無効化・削除・パスワード変更後は、既存セッションでも管理画面を利用できません。

メールは大文字小文字を区別せず検索します。大文字小文字だけ異なる管理者が複数いる場合は、どちらかを勝手に選ばず拒否します。パスワードの前後の空白は削除しません。

同じブラウザーでは `/admin/` と独自管理画面がDjangoのセッションCookieを共有します。同時に別アカウントで確認する場合は別ブラウザーやプライベートウィンドウを使ってください。iPhoneのBearerトークンは別の仕組みです。

## 2. 変更した動作

- 未ログインの `/dashboard/` は、存在する `/login/?next=/dashboard/` に戻ります。
- ログイン成功後は必ず `/dashboard/` に進みます。`next` に外部URLや別画面を指定しても採用しません。
- 管理者トップには仮ページの説明とログアウトボタンがあります。投稿・通報の取得や絞り込みは未実装です。
- ログアウトはCSRFトークン付きのPOSTです。リンクなどによるGETは405、CSRF不備は403になります。CSRFトークンは、外部サイトから意図しない操作をさせないための確認用の値です。
- ログイン済みの通常の `auth.User` は、独自管理画面では403になります。ログイン済みというだけでは許可しません。
- HTML版会員画面はHTTP 410の案内に切り替えました。POSTにも同じ案内を返しますが、CSRF不備はDjangoが先に403で拒否します。旧HTML版のフォーム・ビューは削除し、会員認証はJSON APIに統一しています。HTML版を再開する場合は別途設計・実装が必要です。
- モバイルのAPI応答はJSONの解析、オブジェクト型、成功ステータス、必須文字列を確認します。不正応答は `ApiError` に統一します。401等の失敗ステータスは保持するので、既存の期限切れ処理も継続します。

## 4. 自動テスト

`admin/backend` で実行します。テスト専用設定はメモリ上のDBを使い、テスト終了時に破棄されます。テストDBへの既存マイグレーション適用は自動です。実データ用の `migrate` は必要ありません。

```powershell
.\.venv\Scripts\python.exe -B manage.py test --settings=config.test_settings --verbosity=2
.\.venv\Scripts\python.exe -B manage.py check --settings=config.test_settings
.\.venv\Scripts\python.exe -B manage.py makemigrations --check --dry-run --settings=config.test_settings
```

このPCで仮想環境のPythonが起動できない場合の代替です。既存の仮想環境は削除しません。

```powershell
$env:PYTHONPATH = (Resolve-Path '.venv\Lib\site-packages').Path
$env:PYTHONDONTWRITEBYTECODE = '1'
& 'C:\Users\h_tamaki\.cache\codex-runtimes\codex-primary-runtime\dependencies\python\python.exe' -B manage.py test --settings=config.test_settings --verbosity=2
```

`mobile/frontend` で実行します。

```powershell
node --test tests/auth-validation.test.cjs tests/auth-api.test.cjs
.\node_modules\.bin\tsc.cmd --noEmit
```

通信テストは `fetch` を疑似応答に置き換えます。実サーバーから不正JSONが返されたという意味ではありません。Djangoの実HTTPテストは一時的なローカルサーバーと架空管理者を使います。

旧プレビューは公開URLを復活させていません。旧テンプレート自体の描画は検証対象外で、旧サンプルのデータ選択処理を独立して検証します。現行テンプレートの描画は、認証済み管理者で検証します。

## 5. 手動確認

### PCの管理者画面

1. 利用する開発DBと管理者アカウントを担当者に確認します。通常の `createsuperuser` は `auth.User` を作成するため、そのまま独自管理画面の `AdminUser` にはなりません。
2. 管理者が `AdminUser` に存在し、`is_active=True`・`is_staff=True` であることを確認します。実データの変更は対象を確認し、承認を得てから行います。
3. Djangoを再起動し、未ログインで `/dashboard/` を開くとログイン画面へ戻ることを確認します。
4. 正しい管理者でログインし、トップ表示→再読み込み→ログアウト→アドレス欄から `/dashboard/` を開く、の順で確認します。
5. 誤ったパスワード、未入力、一般会員の認証情報ではトップに入れないことを確認します。

### iPhone

1. [認証README](../mobile/frontend/src/auth/README.md) の接続手順で、Djangoの接続先と `EXPO_PUBLIC_API_BASE_URL` を確認します。既存DBに対するマイグレーションは今回の修正には不要です。
2. DjangoとExpoを再起動し、Expo Goで再読み込みします。
3. 架空の情報で登録→ログイン→仮トップ→ログアウトを確認します。
4. 重複登録、誤ったパスワード、未入力、パスワードの表示切替、通信中の連打防止、通信切断時の説明を確認します。

iPhone実機の表示・操作、実データでの管理者ログインは自動テストでは確認できません。既存管理者の権限、使用DB、管理者作成手順のチーム運用は別途確認が必要です。
