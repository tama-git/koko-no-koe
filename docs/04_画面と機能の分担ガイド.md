# 画面と機能の分担ガイド

対象：これから「ここの声」を分担して実装するメンバー。

この資料のフォルダーは担当場所の整理です。地図・投稿・通報の仕様や、担当者の名前を正式決定するものではありません。

## 1．最初に覚えること

- モバイルはReact Native・Expo・TypeScriptです。画面では `View`（枠）、`Text`（文字）、`Pressable`（押せる部品）などを使います。ブラウザー向けReactの `div` やHTMLのCSSをそのまま使う構成ではありません。
- 管理者画面はDjangoのHTML・CSSです。モバイルの画面ファイルとは別です。
- APIは「画面からサーバーに登録・取得などを頼む窓口」です。画面の完成とAPIの完成は別に確認します。
- 新しいファイルを作っただけでは画面は表示されません。表示する画面を切り替える入口は `mobile/frontend/App.tsx` です。

## 2．モバイルの担当場所

```text
mobile/frontend/
├─ App.tsx                         表示する画面の切り替え
├─ src/
│  ├─ auth/                        会員認証
│  │  ├─ screens/
│  │  │  ├─ LoginScreen.tsx         ログイン画面の入口
│  │  │  └─ RegisterScreen.tsx      登録画面の入口
│  │  ├─ components/AuthForm.tsx    登録・ログイン共通の入力画面
│  │  ├─ styles.ts                 認証画面の色・余白・文字サイズ
│  │  ├─ useAuth.ts                入力値・通信中の状態・認証処理
│  │  ├─ api.ts                    認証サーバーとの通信
│  │  └─ validation.ts             入力内容の確認
│  ├─ home/screens/HomeScreen.tsx  トップ画面とその見た目
│  ├─ shared/components/
│  │  └─ AppScreen.tsx             全画面共通の表示領域・ステータスバー
│  ├─ map/README.md                地図担当の準備場所（機能は未実装）
│  ├─ posts/README.md              投稿担当の準備場所（機能は未実装）
│  └─ reports/README.md            通報担当の準備場所（機能は未実装）
└─ tests/auth-validation.test.cjs  入力チェックのテスト
```

`screens` は画面、`components` は画面で使う部品、`shared` は複数機能で共通利用する場所です。`.tsx` は画面の部品を書けるTypeScriptファイル、`.ts` は主に処理を書くファイルです。

| 担当の例 | 最初に読む・編集する場所 | 他担当と相談する点 |
| --- | --- | --- |
| トップ画面 | `src/home/screens/HomeScreen.tsx` | 地図や投稿一覧の表示方法。現状は仮ページ |
| 登録・ログイン画面 | `src/auth/screens/`、`src/auth/components/AuthForm.tsx`、`src/auth/styles.ts` | 共通フォームの変更は登録とログインの両方に影響する |
| 会員認証の処理 | `src/auth/useAuth.ts`、`api.ts`、`validation.ts` | サーバー側のURL、入力条件、応答形式 |
| 地図 | `src/map/` | 地図ライブラリ、位置情報、閲覧距離の合意 |
| 投稿 | `src/posts/` | 投稿・詳細・一覧の範囲、公開条件、画像の扱い |
| 通報 | `src/reports/` | 通報条件、入力項目、管理者との連携 |
| 管理者画面 | `admin/frontend/templates/admin_side/`、`static/admin_side/` | Django側の認証と権限 |
| サーバー側 | `admin/backend/accounts/`、`config/urls.py` | データの保存先、会員と管理者の区別 |

これは担当の例です。1人が複数を担当しても構いません。誰がどのファイルを編集するかを、作業前に決めてください。

## 3．今の登録・ログインの流れ

1. `App.tsx` が `useAuth()` を一度呼び、ログイン状態を管理します。
2. ログイン前は `LoginScreen` または `RegisterScreen` を表示します。
3. `AuthForm` に入力した値を `useAuth.ts` が受け取り、`validation.ts` で確認します。
4. 問題がなければ `api.ts` がDjangoへ通信します。
5. 登録成功後はログイン画面へ戻ります。ログイン成功後は `HomeScreen` に切り替わります。
6. トップのログアウトボタンが、渡された `onLogout` を呼びます。

`props` は、親の画面から子の部品へ渡す情報や処理です。トップ画面には `busy`（通信中か）、`message`（案内）、`onLogout`（ログアウトの処理）を渡しています。トップ担当者がパスワードやトークンを扱う必要はありません。

`useAuth` は状態と処理をまとめた「カスタムフック」です。状態は、入力値や通信中かどうかなど、操作によって変わる情報です。別の画面で `useAuth()` をもう一度呼ぶと独立した状態を作ってしまうため、今は `App.tsx` で呼んだ結果を渡します。

ログイン状態の保存期間などは認証の試作仕様です。詳細は [認証の説明](../mobile/frontend/src/auth/README.md) を確認してください。

## 4．実装の進め方

### 手順1：担当する小さな範囲と、完成条件を決める

例えばトップ担当なら、最初の作業は「見出しと説明を整え、ログアウトできることを確認する」にします。地図や投稿機能をまとめて完成させようとせず、1回で確認できる範囲に分けます。

作業前に次を決めます。

- 対象画面、編集するファイル、使うデータ。
- 押したボタンが何をするか、前後の画面への移動方法。
- 入力不備、通信中、データなし、通信失敗の表示。
- 未決定事項と、誰に確認するか。

### 手順2：自分の担当ファイルで見た目を作る

トップ画面は `HomeScreen.tsx` の文字や `styles` を編集すると、認証画面を同時に編集せず作業できます。既存のログアウトボタンにある `onPress={onLogout}` と通信中の操作制御も確認してください。

仮データを表示する場合は「仮データ」であると分かる状態にします。実際の保存・通信に成功していないのに、成功した画面を返す処理は追加しません。

登録とログインの画面入口は分かれていますが、入力欄は `AuthForm.tsx` を共用しています。入口ファイルの見出しは個別に編集できます。入力欄の配置や共通スタイルを変える場合は両画面を確認し、同じファイルを2人で同時に編集しないようにします。

### 手順3：必要になったファイルだけ追加する

投稿機能を作る場合の例です。以下は実装済みファイルではありません。合意した機能の範囲に応じて追加します。

```text
src/posts/
├─ screens/PostDetailScreen.tsx   投稿詳細の画面
├─ components/PostCard.tsx        一覧に表示する投稿1件の部品
├─ api.ts                        投稿の取得・送信
└─ types.ts                      投稿データの項目と型
```

部品を切り出すのは、繰り返し使う・担当を分ける・ファイルが読みにくいといった理由があるときです。最初から空のファイルを大量に作る必要はありません。

新しい画面への切り替えは、`App.tsx` を扱う統合担当者と相談します。今は認証の2画面とトップの切り替えだけです。複数画面の「戻る」操作などが必要になったら、画面遷移の設計やライブラリの導入を相談します。

### 手順4：API担当と送受信の約束を合わせる

画面から何を送り、サーバーから何が返るかを先に確認します。

| 確認する項目 | 意味 |
| --- | --- |
| URL・HTTPメソッド | 通信先と、取得・登録などの操作 |
| 送信項目 | 例：メールアドレス、パスワード |
| 成功時の応答 | 画面が次に使うデータや完了の通知 |
| 失敗時の応答 | 入力不備・権限不足・通信失敗の区別 |
| ログインと権限の確認 | 誰が、その操作をしてよいか |

会員の登録・ログインはすでに試作があるため、同じAPIを別の場所に重複作成しません。投稿・通報のDjangoアプリを追加するかなど、バックエンドの配置は担当者と相談します。今のバックエンドを無断で別フォルダーへ移動しません。

### 手順5：小さく確認してからチームに渡す

`mobile/frontend` で次を実行します。

```powershell
.\node_modules\.bin\tsc.cmd --noEmit
```

これは、型（文字・数値などの情報の種類）と部品の受け渡しが合っているかを調べます。

```powershell
node --test tests/auth-validation.test.cjs
```

これは、既存の認証入力チェックを確認します。地図や投稿の動作を保証するテストではありません。

その後、Expo Goで変更した画面と関連画面を確認します。最低限、登録→ログイン→トップ→ログアウトと、未入力・パスワード表示切り替え・通信失敗時の表示を確認してください。実機で確認できなかった項目は、引き継ぎに書きます。

## 5．接続先とデータの注意

各自の `mobile/frontend/.env.local` に、自分が接続する開発サーバーのアドレスを設定します。設定は [認証の説明](../mobile/frontend/src/auth/README.md) にあります。ほかの人のPCのアドレスを、そのまま使わないでください。Expoのログインと「ここの声」の会員ログインは別です。

`.env.local` やデータベース、パスワード、トークンはGitHubに送りません。`EXPO_PUBLIC_*` の値はアプリに含まれるため、秘密情報を入れてはいけません。Wi-Fiや設定値を変更したらExpoを再起動します。

データベースの準備や変更をするときは、使う環境・保存済みデータ・担当者を確認してから行います。このPCに作った確認専用DBは、ほかのメンバーへ自動で共有されません。HTTPで確認する場合は、他で使っていない仮の情報を使います。

## 6．共同作業でぶつかりやすいファイル

`App.tsx`、`src/auth/useAuth.ts`、`src/auth/components/AuthForm.tsx`、`src/shared/`、`admin/backend/config/urls.py`、依存関係の一覧は、複数担当に影響する場所です。変更するときは事前に担当者と編集範囲を合わせます。

Git操作は [チームの起動手順の9章](01_チームの起動手順.md#github-upload) を参照してください。未コミットの変更を削除してから開始する操作はしません。共有時には、次の内容を伝えます。

- 変更した画面・機能とファイル。
- 操作手順と期待する結果。
- 確認した結果と、未確認・未実装の項目。
- 別担当に接続・確認してもらう箇所。

コミット・push・PRなどは、チームの確認と、この作業の承認ルールに従って行います。

## 7．まだ決める必要があること

閲覧距離の500mと250m、いいね済み投稿の圏外閲覧、管理者の対象端末について資料間に不一致があります。地図ライブラリや認証の継続方法も、コードが存在するだけで正式決定とは扱いません。関係する機能を実装する前に、最新のチーム合意を確認してください。
